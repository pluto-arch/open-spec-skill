# 01 需求变更分析参考

## 目标

把用户输入转成可追溯的变更范围、需求条目和验收口径，明确本次变更影响面与风险。

## 输入清单

- 用户原始需求与背景
- 当前系统 / 文档现状
- 时间、成本、合规、性能等约束
- 历史版本、兼容性与依赖边界

## 执行步骤

1. 变更澄清：明确“为什么改”“改什么”“不改什么”。
2. 影响分析：列出受影响文档、模块、数据和兼容性边界。
3. 场景拆分：按主路径、异常路径、边界路径整理场景。
4. 需求收敛：形成 FR / NFR 与验收标准。
5. 风险登记：记录兼容性、迁移、发布、依赖风险。
6. 缺口分级：将信息缺口按 `Blocker/Assumption/Nice-to-know` 分类。
7. 用户补齐：若存在 `Blocker`，输出问题包并暂停。

## FR 编写规范

- 一条 FR 只描述一个可交付能力。
- 使用“触发条件 + 系统行为 + 可验证结果”的结构。
- 必须能被至少一个验证项覆盖。

推荐句式：

- 当 <触发条件> 发生时，系统应 <行为>，并且 <可验证结果>。

## NFR 编写规范

- 约束必须可量化。
- 至少包含度量方式与阈值。

## 自检清单

- [ ] FR 全部具备唯一 ID 且可测试
- [ ] In Scope / Out of Scope 明确
- [ ] 影响文档、影响模块、兼容性影响已明确
- [ ] NFR 量化且可观测
- [ ] 每条风险均有缓解策略或待决计划
- [ ] 信息缺口集中记录，无散落待办
- [ ] 所有 `Blocker` 已转成待用户确认问题，未确认前阶段状态为 `NEEDS_USER_INPUT`

## 产出映射

- 主文档：`01-change-analysis.md`
- 变更请求：`00-change-request.md`
- 阶段交接：`08-task-handoff.md`

## Input Contract（输入契约）

- 任务目标：明确本次变更范围、影响面与 FR/NFR。
- 必读输入：用户目标、约束、历史背景、已知依赖与兼容要求。
- 上游引用：变更请求（如有）与关键上下文摘要。
- 输出约束：FR/NFR 必须唯一编号并可验证。

## Output Contract（输出契约）

- 必交文档：`01-change-analysis.md`（变更场景补 `00-change-request.md`）。
- 必含内容：范围、影响分析、FR/NFR、验收标准、信息缺口、风险假设。
- 追溯锚点：FR/NFR/CR/REV ID。
- 交接摘要：写入 `08-task-handoff.md` 的结论、风险、下阶段输入。
- 若存在 `Blocker`：门禁状态必须返回 `NEEDS_USER_INPUT`，并附待用户回答的问题包。
